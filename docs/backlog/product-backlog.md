## 1. 故事格式约定

```
US-xx  作为 <角色>，我希望 <能力>，以便 <价值>。
```

角色只有四种：**访客 / 注册用户 / 内容作者 / 管理员**（教师是"管理员"的一种）。
不写"系统应该…""用户可以…"这类没有角色的句子。

## 3. MVP 切片说明（为什么是这 5 条）

Walking Skeleton 的判定标准是 **"端到端最薄的一条线，跑通后每个新故事都只是加一块肉"**：

```
US-01/02 注册登录  →  US-04 提问  →  US-03 列表  →  US-05 详情
   （有身份）           （产生数据）      （看到数据）     （消费数据）
```

- 少了 US-01/02：所有内容没有归属，后面投票、声誉都无从谈起；
- 少了 US-04：库里没有数据，列表和详情是空壳；
- 少了 US-03/05：写进去的东西看不到，Sprint Review 无法演示。

**有意排除在 MVP 之外**：投票、采纳、评论、标签、声誉（属于 Sprint 3 的"价值闭环"），
以及搜索、通知、徽章（Sprint 4）。理由：它们都建立在"有问题、有回答"之上，先有骨架再加肉。

## 5. 优先级排序依据（价值 / 成本 二维矩阵）

| 象限 | 判定 | 故事 |
|---|---|---|
| 高价值 · 低成本 → **立即做** | 走骨架必需，且 1 个 Sprint 内可交付 | US-01、US-02、US-03、US-04、US-05、US-07、US-08 |
| 高价值 · 高成本 → **规划做** | 价值明确但要专门排期 | US-06、US-11、US-12、US-13 |
| 低价值 · 低成本 → **顺手做** | 有空档再补 | US-09、US-15、US-21、US-22、US-23 |
| 低价值 · 高成本 → **先不做** | 本期明确砍掉，写进"不做清单" | US-18、US-24、US-19（依赖治理策略未定） |

> 现场话术：PO 只回答一个问题——"如果这个 Sprint 只能交付一条，交哪条？"
> 剩下的按同一逻辑重复，避免"所有故事都重要"。

## 6. 明确不做（Out of Scope，防止范围蔓延）

1. 移动端 App、微信小程序（Sprint 4 之后再评估）；
2. 富文本所见即所得编辑器（本期只做 Markdown）；
3. 私信 / 实时聊天；
4. 与教务系统对接课程数据；
5. 内容推荐算法（本期只做"最新"排序）。
